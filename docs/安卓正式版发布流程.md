# 安卓正式版发布流程

正式发布依次更新版本、构建并校验签名 APK、发布 GitHub Release、验证 GitHub Pages 和 App 内更新。下文以从 1.0.2 发布到 1.0.3 为例，命令从仓库根目录在同一个 PowerShell 会话中执行。

## 1. 更新版本并提交

编辑 [update.json](../android/app/src/main/assets/www/update.json)，将 `versionCode` 设为大于已发布版本的整数，`versionName` 使用三段数字，`apk` 使用约定的附件名。Gradle 从这份文件读取版本，打包时也会把它放进 APK。

```json
{
  "versionCode": 5,
  "versionName": "1.0.3",
  "apk": "NainaiPaohuzi-1.0.3-release.apk"
}
```

先在 `main` 上提交准备发布的功能修改，再提交版本号。等这次推送的 Pages 工作流成功后继续。此时线上更新源仍指向已发布的正式版，待新 Release 发布后才切换。

```powershell
if ((git branch --show-current).Trim() -ne 'main') { throw 'Switch to main before releasing.' }
$releaseInfo = Get-Content android/app/src/main/assets/www/update.json -Raw | ConvertFrom-Json
$releaseTag = "v$($releaseInfo.versionName)"
node --test
if ($LASTEXITCODE -ne 0) { throw 'Tests failed.' }
git add -- android/app/src/main/assets/www/update.json
git commit -m "Bump Android to $($releaseInfo.versionName)" -- android/app/src/main/assets/www/update.json
if ($LASTEXITCODE -ne 0) { throw 'Version commit failed.' }
if (git status --porcelain) { throw 'Commit the remaining release changes before building.' }
git push origin main
if ($LASTEXITCODE -ne 0) { throw 'Push failed.' }
$releaseCommit = (git rev-parse HEAD).Trim()
```

## 2. 构建正式签名 APK

使用 JDK 17 和 Android SDK Platform 35。设置 `ANDROID_HOME` 指向 SDK，或在 `android/local.properties` 填写 `sdk.dir`。APK 的包名是 `io.github.hijie.nainaipaohuzi`。后续发布沿用这个包名和「衡阳跑胡子」正式签名，用户才能覆盖安装并保留本地数据。

本机签名文件位于 `%LOCALAPPDATA%\NainaiPaohuzi\signing\`，密钥库为 `nainaipaohuzi-release.p12`，别名为 `nainaipaohuzi-release`。下面的命令用当前 Windows 账号解密密码，临时传给 Gradle。换电脑时，从备份恢复同一密钥库，并用 `Read-Host -AsSecureString` 在本机输入备份密码替代解密步骤。密钥库和密码单独备份，留在仓库外。

```powershell
$signingDir = Join-Path $env:LOCALAPPDATA 'NainaiPaohuzi/signing'
$encryptedPassword = Get-Content (Join-Path $signingDir 'release-password.dpapi') -Raw
$securePassword = ConvertTo-SecureString $encryptedPassword.Trim()

Push-Location android
try {
    $env:PAOHUZI_SIGNING_STORE_FILE = Join-Path $signingDir 'nainaipaohuzi-release.p12'
    $env:PAOHUZI_SIGNING_KEY_ALIAS = 'nainaipaohuzi-release'
    $env:PAOHUZI_SIGNING_STORE_PASSWORD = [System.Net.NetworkCredential]::new('', $securePassword).Password
    $env:PAOHUZI_SIGNING_KEY_PASSWORD = $env:PAOHUZI_SIGNING_STORE_PASSWORD

    .\gradlew.bat :app:assembleRelease --no-daemon --console=plain
    if ($LASTEXITCODE -ne 0) { throw 'Release build failed.' }
} finally {
    Remove-Item Env:PAOHUZI_SIGNING_STORE_FILE,Env:PAOHUZI_SIGNING_KEY_ALIAS,Env:PAOHUZI_SIGNING_STORE_PASSWORD,Env:PAOHUZI_SIGNING_KEY_PASSWORD -ErrorAction SilentlyContinue
    Pop-Location
}
```

复制构建产物，文件名与 `update.json` 的 `apk` 字段一致。以下命令通过 `ANDROID_HOME` 找到 Android SDK Build Tools 34.0.0，校验 APK 签名并显示包名和版本。

```powershell
$apkDir = 'android/app/build/outputs/apk/release'
$apkFile = Join-Path $apkDir $releaseInfo.apk
Copy-Item -LiteralPath (Join-Path $apkDir 'app-release.apk') -Destination $apkFile
$buildTools = Join-Path $env:ANDROID_HOME 'build-tools/34.0.0'
& "$buildTools/apksigner.bat" verify --print-certs $apkFile
if ($LASTEXITCODE -ne 0) { throw 'APK signature verification failed.' }
& "$buildTools/aapt.exe" dump badging $apkFile | Select-String '^package:|^sdkVersion:|^application-debuggable'
Get-FileHash -Algorithm SHA256 -LiteralPath $apkFile
```

确认 `versionName`、`versionCode` 与 `update.json` 一致，输出中没有 `application-debuggable`，并记录 APK 的 SHA-256。当前正式证书的 SHA-256 指纹为 `d716265ad08deb67313c251f271c16667ded9f8c73aa8dccdf80a8c2bcc03e9a`。

## 3. 发布 GitHub Release

给构建使用的提交打标签并推送。上传前用 `git ls-remote` 核对远端标签指向的提交。

```powershell
git tag $releaseTag $releaseCommit
git push origin "refs/tags/$releaseTag"
git ls-remote --tags origin "refs/tags/$releaseTag"
```

在仓库的 [Releases](https://github.com/hi-jie/NainaiPaohuzi/releases) 页面创建草稿，选择刚推送的标签，填写更新说明，上传 `$apkFile` 对应的正式包。确认只上传一个符合 `NainaiPaohuzi-<版本>-release.apk` 命名的 APK，选为 **Latest release**，再发布。[GitHub Release 操作说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository#creating-a-release)

## 4. 确认 Pages 部署和下载

正式 Release 发布后，[Pages 工作流](../.github/workflows/pages.yml) 会从 `main` 触发实际部署。进入 [Actions](https://github.com/hi-jie/NainaiPaohuzi/actions/workflows/pages.yml)，确认 `main` 上的部署运行成功。Release 标签触发的任务负责发起部署，实际部署运行的分支是 `main`。

工作流下载最新正式 Release 的 APK，从包内读取 `assets/www/update.json`，把安装包和对应的版本信息放进同一份 Pages 产物。每次部署只包含最新正式版的 APK。

1. 打开 [线上 update.json](https://hi-jie.github.io/NainaiPaohuzi/update.json)，核对版本号、内部版本号和 APK 文件名。
2. 从 Pages 下载该文件，比较它与本地正式包的 SHA-256。
3. 检查上一个版本的 Pages APK 地址返回 `404`，旧版仍可从 GitHub 的对应 Release 下载。

```powershell
$pagesBase = 'https://hi-jie.github.io/NainaiPaohuzi/'
$stamp = [DateTimeOffset]::UtcNow.ToUnixTimeSeconds()
$online = Invoke-RestMethod "${pagesBase}update.json?verify=$stamp"
if ($online.versionCode -ne $releaseInfo.versionCode -or
    $online.versionName -ne $releaseInfo.versionName -or
    $online.apk -ne $releaseInfo.apk) { throw 'Pages version does not match the release.' }

$downloadedApk = Join-Path $env:TEMP "paohuzi-pages-$($releaseInfo.apk)"
curl.exe --fail --location --output $downloadedApk "${pagesBase}$($online.apk)"
if ($LASTEXITCODE -ne 0) { throw 'Pages APK download failed.' }
if ((Get-FileHash -LiteralPath $downloadedApk).Hash -ne
    (Get-FileHash -LiteralPath $apkFile).Hash) { throw 'Pages APK SHA-256 does not match.' }
```

如果 Release 已发布而线上版本未切换，先核对 Latest 标记、附件名称和 APK 内的 `update.json`。修正后可在 [Pages 工作流](https://github.com/hi-jie/NainaiPaohuzi/actions/workflows/pages.yml) 上选择 `main` 并点 **Run workflow**。补发修复版时使用更大的 `versionCode`。

## 5. 在手机上验证升级

用已带更新入口的旧正式版测试。在「设置 → 检查更新」确认只在点击后查询，看到新版本后先点取消，再检查并确认下载。确认进度条替换检查按钮，下载完成后出现「安装」。需要允许此来源安装时，按系统提示授权，再完成系统安装。升级后查看设置页的版本号，并核对积分和存档。最后再次检查更新，应显示「已是最新版本」。

只做本地同版本试包时，可沿用当前版本号和正式签名。App 以 `versionCode` 判断有没有新版本，同版本试包应通过手动安装验证界面。
